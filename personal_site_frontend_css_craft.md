# PERSONAL SITE — Frontend Implementation & CSS Craft

**Статус:** постоянная инженерная инструкция кодовому агенту. **Это не задание на изменение сайта.**
**Проект:** `thaelr/personal-site`. Локальный путь и ветку выдаёт пользователь; фактические инструменты и зависимости проверяются в рабочей копии.

## 1. Разделение ответственности

- **Художественный замысел** (композиция, типографические акценты, выбор референсов, анимационная режиссура, содержание) утверждается вне кодового агента.
- **Техническое решение** (CSS, структура компонентов, корректность адаптива, доступность, минимальная реализация) выбирается агентом **только в пределах конкретного утверждённого задания**.
- Агент **исполняет**, а не выступает вторым арт-директором. Он не проводит самостоятельный дизайн-ресерч, не ищет «более эффектные» референсы, не додумывает незаданные состояния и не меняет UX ради собственного представления об удобстве или красоте.
- При художественной неопределённости: **остановить только соответствующий участок**, показать фактическое текущее поведение, назвать недостающее решение и минимальные варианты; не выбирать самому. Независимую, явно определённую работу можно завершить.
- Инженерная свобода остаётся: выбрать надёжный CSS/React-метод при **одном и том же наблюдаемом результате**; исправить подтверждённую ошибку в рамках разрешённой области, проверить и отладить реализацию.

## 2. Порядок источников

1. **Текущее конкретное ТЗ + утверждённый целевой макет/скриншот/демо с указанной механикой** — то, *что должно получиться*. Если документация конфликтует с явным новым решением, приоритет у нового решения.
2. **Постоянные инженерные ограничения (этот файл)** — *как работать*.
3. **Актуальный локальный код** — то, *как сайт работает сейчас*, и источник действующих технических контрактов.
4. **Art Direction & Design Principles** — дополнительный **контекст ограничений**, а не каталог решений, которые агент вправе выбирать или воплощать сам. Передаётся только при необходимости и не расширяет объём ТЗ.
5. **Внешние референсы** — используются строго в назначенном фрагменте: *какой именно элемент, какое именно поведение*. Сама ссылка не разрешает копировать другие эффекты, цвета или структуру.

Если требуемое состояние не определено в ТЗ, референсе или макете, не придумывать его. Точное сопоставление с референсом имеет смысл только при доступной версии референса; иначе сообщить об ограничении. Внешнюю техническую документацию читать по необходимости для **API/браузерного поведения**, но не для нового художественного решения.

## 3. Кодовая карта (ориентир, не обязательный список чтения)

- `src/index.css` — сетка, палитра, типографика, media queries, состояния, анимации.
- `src/App.tsx` — секции, scroll tracking, URL hash.
- `src/components/Nav.tsx` — правое desktop-меню, мобильная навигация.
- `src/components/HomeSection.tsx` — hero, портрет, CTA со скобками.
- `src/components/WorkSection.tsx` — текущая структура WORK.
- `src/components/AboutSection.tsx` — раскрытия, карьерная геометрия, авторские текстовые реакции.
- `src/components/ContactSection.tsx` — контакты и CTA.
- `package.json`, `vite.config.ts`, `.github/workflows/deploy.yml` — только если задание касается сборки, роутинга или публикации.

Репозиторий: https://github.com/thaelr/personal-site — **не подменяет локальную ветку**. Публичная версия: https://thaelr.github.io/personal-site/ — контекст старого поведения, **не новый целевой макет**.

## 4. Сохранение поведения и внешнего вида

При техническом рефакторе без отдельного дизайнерского задания сохраняй:

- существующую композицию, 10-колоночную desktop-сетку, положение правого меню, портрет, структуру HOME/WORK/ABOUT/CONTACT;
- текст, метрики, ссылки, порядок блоков, пасхалки и нестандартные интеракции;
- текущие осмысленные скобки, зелёные состояния и авторские эффекты, даже если они выглядят необычно;
- совместимость клавиатуры/тач-ввода, активных состояний и адресной навигации.

Не добавлять по собственной инициативе новые цвета, подложки, «красивые» рамки, подчёркивания, типографику, иконки, hover, scroll reveal, System Notices, звук, video/motion-сцены или компоненты. **Сдержанность в базовом интерфейсе и абсурд в выбранных местах — художественный принцип, но не задание создать эти места.**

## 5. CSS Engineering

- Перед изменением определить, какое правило реально применено: cascade, specificity, media queries, layout, containing block, stacking context, overflow и transform.
- Исправлять первопричину; не наращивать побочные переопределения в конце `index.css` и не скрывать переполнение глобальным `overflow-x: hidden`.
- Grid/Flex/subgrid, CSS custom properties и локальные селекторы — по фактической необходимости. Не вводить CSS-in-JS, новую дизайн-систему, Tailwind-миграцию или библиотеку компонентов ради порядка.
- Учитывать существующие `--layout-page-scale`, `--hero-scale`, `--work-scale`, `--about-scale`: сейчас они связывают размеры геометрии и текста. При исправлении читабельности **не менять общую композицию без утверждённого целевого состояния**.
- Проверять реальный порядок чтения и фокуса при `display: contents`, `order`, аккордеонах, fixed/sticky-слоях и responsive перестановке.
- Для анимаций соблюдать физическую непрерывность и производительность; не ломать измерение `ResizeObserver` и scroll-geometries ABOUT. `prefers-reduced-motion` сохраняет функциональность.

## 6. Кинетика — только по отдельному ТЗ

Направления будущего дизайна: **Bracket/Crosshair Interaction**, **Kinetic Disclosure**, **Spatial Transition**. Это **не разрешение внедрять их сейчас**.

Если задача конкретно утверждает одну механику, реализовать только её и только в названных элементах. Для сравнения использовать указанный target, а не собственную трактовку «fashion», «premium» или «живее». Не добавлять Motion, GSAP, router и иные зависимости без технической необходимости и разрешённого scope.

Основной сохранённый художественный референс (для будущих заданий): https://codefronts.com/motion/css-link-effects/crosshair-brackets/ . Самостоятельная реализация референса без ТЗ **запрещена**.

## 7. Рабочая процедура

1. Убедиться в правильном репозитории и ветке; `git status --short` до правок. Не стирать пользовательские изменения.
2. Прочитать **только** конкретное ТЗ и релевантный исходный код. Для сложной задачи дать короткий технический план; если предусмотрен gate согласования — **остановиться до разрешения**.
3. Подтвердить симптом дефекта или текущую механику изменяемого компонента. Отделить факт от гипотезы.
4. Изменить только файлы, непосредственно необходимые для разрешённой задачи. Без unrelated cleanup и без «раз уж здесь — улучшил».
5. Проверить наблюдаемое поведение; для визуального изменения — браузер, реальные интеракции, размеры экрана и сравнение **с утверждённым target**, если он предоставлен. Для технического исправления — отсутствие визуальных регрессий по baseline.
6. Выполнить минимальные соразмерные проверки (`typecheck`, build, целевые тесты — какие существуют и уместны). Падающий тест не есть новая спецификация. Не ослаблять assertions ради PASS.
7. Проверить diff и статус; выдать кратко: изменённые файлы, наблюдаемое до/после, проверки с результатами, непроверенное, блокеры. **Остановиться после указанного этапа**.

Если браузер/эталон недоступен, не утверждать, что визуальное совпадение подтверждено.

## 8. Безопасность и ограничения

- Без отдельного разрешения: **никаких commit, push, deploy, rebase, reset, force push**. Push в `main` запускает GitHub Pages — возможна публикация.
- Не менять секреты, runtime config и внешние системы без отдельного согласования.
- Не подменять фиксацию ошибки изменением продуктового поведения. Не изобретать API, маршруты, тексты, assets и конфигурационные переменные.
- Не запускать избыточные анализаторы, многорепозиторные исследования или новые harness-слои ради локального изменения.
- Если обнаружен дефект вне текущего scope — документировать как находку, **не исправлять автоматически**.

**Критерий:** точно реализовано утверждённое решение, сохранено всё не затронутое задачей, исправление доказано проверками. Не художественная интерпретация агента.
